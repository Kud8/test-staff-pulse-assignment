# Модель данных

GET /api/org-tree возвращает плоский массив `{id, name, parentId, headcount, budget, performance, updatedAt}`. id, name и parentId (кроме null) — непустые строки без пробелов по краям: такие значения отклоняются, а не нормализуются. parentId корня — null; допускается несколько корней. Пустой массив корректен.

headcount — неотрицательное безопасное целое; budget — конечное неотрицательное число в рублях до MAX_SAFE_INTEGER; performance — конечное число 0–100. Это **собственные**, а не суммарные показатели. updatedAt — ISO 8601 с Z или смещением часового пояса. Клиент также проверяет уникальность ID, существование родителей и отсутствие циклов за O(n).

Набор: 4 дивизиона × (1 дивизион + 3 отдела + 6 команд) = 40 узлов, 3 уровня. Имена, значения и дата воспроизводимы при перезапуске. Есть узел с нулевой численностью. Модель строит byId, children и roots; первые два уровня раскрыты.

## Координаты снимка
Тело ответа остаётся плоским массивом, а положение снимка в потоке передаётся заголовками: `X-Org-Session` — идентификатор запуска сервера, `X-Org-Version` — версия снимка, целое ≥ 1. Ответ без корректных заголовков клиент считает ошибкой. Каждый запуск сервера получает новую сессию, поэтому после перезапуска старые версии заведомо недействительны.

## Агрегация
Для каждого узла хранятся суммы по узлу и всем его потомкам: `headcount`, `budget` и `weightedPerformance` — сумма `performance × headcount`. Средняя эффективность выводится из них: `weightedPerformance / headcount`, при нулевой численности — `null`, в интерфейсе «—». Средние значения потомков не усредняются.

Обход один: итеративный pre-order даёт строки в порядке дерева и уровень вложенности, обратный проход по этому же списку добавляет суммы каждого узла в его родителя, потому что в pre-order каждый потомок стоит после своего предка. Сложность O(n), рекурсии нет, поэтому глубина недоверенных данных не переполняет стек.

Агрегация выполняется один раз на снимок данных и мемоизируется. Фильтр и сортировка получают уже готовые строки, не меняют их значения и не пересчитывают суммы. Уровень: 1 — дивизион, 2 — отдел, 3 — команда, глубже — «Уровень N».

## Живой поток: WebSocket `/api/live`
Сервер шлёт три вида сообщений, у всех есть `session` и `version`:

| Тип | Когда | Поля |
|---|---|---|
| `hello` | сразу после открытия сокета | `{type, session, version}` |
| `ping` | раз в `LIVE_HEARTBEAT_MS` (по умолчанию 5000 мс) | `{type, session, version}` |
| `patch` | при изменении значений узла | `{type, session, version, id, changes, updatedAt}` |

`changes` содержит хотя бы одно из полей `headcount`, `budget`, `performance` в тех же границах, что и схема узла. Патчи меняют только значения существующих узлов: добавление, удаление и перемещение исключены, поэтому структура дерева живёт столько же, сколько снимок. Сервер проверяет собственный патч своей же схемой прежде чем его разослать.

Правила клиента:
- `version ≤ нашей` — дубликат или устаревшее сообщение, игнорируется;
- `version = нашей + 1` — патч применяется, версия снимка растёт;
- `version > нашей + 1` — часть сообщений потеряна, нужен один перезапрос снимка;
- патч ничего не изменил по значениям — версия всё равно принимается, иначе следующий патч выглядел бы пропуском;
- `id` неизвестен — структуры разошлись, нужен перезапрос;
- `session` не наша — сервер перезапустился, нужен перезапрос;
- `hello` или `ping` той же сессии с версией больше нашей — мы отстали, нужен перезапрос; равные и старые версии игнорируются.

Обычные патчи не вызывают GET: плоские узлы и инкрементальные агрегаты атомарно записываются в Query-кэш. Запоздавший HTTP-снимок той же сессии с меньшей или равной версией не заменяет кэш.

При разрыве согласованности выполняется один GET восстановления; новые сообщения его не отменяют. До 256 неприменённых патчей сохраняются и после ответа воспроизводятся по порядку, дубликаты удаляются. Чужая сессия начинает новый буфер. При переполнении удаляется самый старый патч: оставшийся пропуск закрывается следующим снимком. После ошибки или неполного восстановления запрос повторяется с задержкой 1, 2, 4, 8, затем максимум 10 секунд. После успешного восстановления счётчик сбрасывается. Размонтирование очищает буфер и таймер; запоздавшее завершение запроса больше не применяет буфер. Отдельно сохраняются стандартные фоновые обновления устаревшего Query-кэша при фокусе и восстановлении сети.

## Инкрементальный пересчёт
Патч меняет значения одного узла, поэтому суммы меняются только у него и его предков. Клиент считает дельты `headcount`, `budget` и `weightedPerformance`, проходит по цепочке предков и пересчитывает среднюю эффективность из обновлённых сумм. Строки вне цепочки сохраняют ссылки, а если все дельты нулевые, предки не пересчитываются вовсе. Результат совпадает с полной агрегацией снимка — это закреплено тестом и проверено фаззингом на 2000 патчей, расхождение ровно ноль: все суммируемые величины здесь целочисленные. Дрейф чисел с плавающей точкой возможен только если сервер начнёт присылать дробные бюджеты; перезапрос снимка возвращает точные значения.

Результат применения патча разделён на две карты изменённых ячеек: собственные значения узла и агрегаты узла вместе с его предками. Дерево подсвечивает первое, таблица — второе, поэтому в дереве не мигают ячейки, значения которых не менялись. Подсветка живёт 1.5 с и ведётся по каждой ячейке отдельно: изменение бюджета не гасит подсветку численности.

## AI-фильтр
POST `/api/search`: `{query:string}`, 1–500 символов, тело до 4096 байт. Успех: `{mode:"ai", filter}`; fallback: `{mode:"text", reason}`. Причины: `unconfigured`, `timeout`, `unavailable`, `invalid`, `unsupported`, `busy`. Busy возвращает HTTP 429, невалидный запрос — 400, превышение размера — 413.

`filter` содержит ровно `name`, `level`, `headcount`, `budget`, `performance`. Все поля обязательны и nullable. `name` — подстрока до 120 символов, `level` — целое 1–100. Числовое условие: `{min: bound|null, max: bound|null}`, где `bound = {value:number, inclusive:boolean}`. Нижняя граница не больше верхней; равные границы допустимы только при включении обеих. Числа неотрицательны и конечны; эффективность до 100, прочие границы до MAX_SAFE_INTEGER. Неизвестные поля отклоняются, никакого кода/выражений.

Все условия соединяются И и проверяются по агрегированным строкам после полной/инкрементальной агрегации; поиск не меняет поддерево. `performance:null` не удовлетворяет числовому условию. При отсутствии условия строки с null остаются. Интерпретация собирается из фактически применённой схемы; обновления данных заново проверяют условия, не вызывая LLM.
